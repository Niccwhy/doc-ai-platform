# 数据库设计 v3 —— 多租户文档处理平台

> 目标库：PostgreSQL 16.15 / pgvector 0.8.7 / pg_trgm
> DDL：`sql/init/002_schema_v3.sql`（重建脚本，18 表）
> 上一版：`sql/legacy/001_schema_v1.sql`（v1）、`sql/init/001_schema.sql`（v2，12 表）
> 更新：2026-11-03

## 1. 设计目标与原则

| 原则 | 落地方式 | 为什么这么做 |
|---|---|---|
| **租户隔离是物理约束，不是约定** | 每张业务表带 `dept_id`；跨表引用用**复合外键** `(fk_id, dept_id)` | 单靠 Service 层过滤，任何一个新接口漏写 `where dept_id=?` 就是数据泄露。复合外键让"部门 A 引用部门 B 的数据"在数据库层无法写入 |
| **软删除必须与唯一约束共存** | 唯一索引全部带 `WHERE deleted_at IS NULL` | 否则"删掉的账号/文件"会永久占用唯一键，出现"删了却建不回来"的死局 |
| **表结构可演进** | 主键 `GENERATED BY DEFAULT AS IDENTITY`；状态用 `VARCHAR + CHECK`；新列一律可空或带默认 | IDENTITY 兼容 MyBatis-Plus `IdType.AUTO` 且允许迁移时显式指定 id；VARCHAR 改枚举值只需改 CHECK，不用改类型 |
| **时间无歧义** | 全库 `TIMESTAMPTZ NOT NULL DEFAULT now()` | 邮件来自外部时区，`TIMESTAMP` 在跨时区/夏令时/容器时区漂移时会算错 SLA 与耗时 |
| **审计不可被业务删除** | `task_log` / `sys_audit_log` 为 append-only，与业务表**不建立级联** | 一旦 `ON DELETE CASCADE`，删任务就等于销毁证据链 |
| **写路径短、读路径索引化** | 高频查询逐条设计索引；用部分索引把"热数据"和"历史数据"分开 | 见第 5 节 |

## 3. 实体关系

```
sys_dept 1──N sys_user            （dept_id，RESTRICT）
sys_dept 1──N document / task / sys_tag / extract_schema ...
sys_dept 1──N dept_email_config 1──N email_inbox ──N─1 document（认领后）
sys_user 1──N document(uploader_id) / task(creator_id, assignee_id)

document 1──N document_block          （CASCADE，块随文件销毁）
document 1──N document_version        （CASCADE）
document N──N sys_tag                 （document_tag_rel，复合外键）
document(TEMPLATE) 1──N template_field_mapping ──N─1 extract_schema

task N──N document                    （task_document_rel）
task 1──N extract_result 1──N extract_result_history
document_block 1──N extract_result    （evidence_block_id，SET NULL，证据另有文本快照）
task 1──N task_log                    （无级联，append-only）
```

关键点：

- **`extract_result` 是"多候选 + 单选终稿"**：一个任务含 N 份文档，同一字段（如"总价"）可能在多份报价单里出现。所有候选都保留，`is_selected` 标记终稿，并由部分唯一索引保证**每字段至多一个终稿**。
- **`evidence_block_id` 与 `evidence_text` 并存**：块可能因重新解析被清理，`SET NULL` 后仍能凭文本快照追溯证据（纯外键做不到这一点）。
- **`template_field_mapping` 是填表链路的地基**：没有它，`field_key` 无法映射到 Word 书签或 Excel 单元格，FILL 任务只能靠代码硬编码。

## 4. 关键设计决策与权衡

### 4.1 文件去重：不做唯一约束

| 方案 | 后果 |
|---|---|
| `UNIQUE(dept_id, sha256)`（v2 做法） | ① 与软删冲突：删除后无法重传；② 同一客户重复发同一合同属正常业务，被硬拒；③ 邮件附件与内部上传同一文件互撞 |
| **v3：非唯一索引 + 查重提示** | 允许重复；幂等性由 `email_inbox UNIQUE(config_id, message_uid, attachment_index)` 保证；上传时 `idx_doc_sha` 可毫秒级查出"已有同名文件"供用户确认 |

代价：失去"物理上不可能重复"的强保证，服务层需要实现"提示并让用户选择复用/新建"。

### 4.2 授权码加密

`auth_code_enc TEXT` 存密文，`auth_code_kid` 记录密钥版本以便轮换。接口层只写不读（返回掩码）。
代价：引入密钥管理（环境变量/KMS）；排障不能直读原值；应用启动需要密钥，否则邮箱功能不可用（应降级而非崩溃）。

### 4.3 状态机与并发认领

`task.status` 六态：`PENDING → ASSIGNED → PROCESSING → COMPLETED / FAILED / CANCELLED`。

- **`ASSIGNED` 不可省**：v2 只有四态，无法表达"已派发但未开工"，自动分配引擎每次都会重新派发给同一人。
- **认领用行级条件更新**：`UPDATE task SET status='PROCESSING', claimed_at=now(), lease_expires_at=now()+interval '30 min', version_no=version_no+1 WHERE id=? AND status='ASSIGNED' AND version_no=?`，影响行数为 0 即认领失败。
- **租约回收**：`lease_expires_at` 超时后允许其他处理员重新认领，避免"人离职/浏览器崩溃导致任务永久卡住"。

### 4.4 热点行：进度不落库

`task.progress` 在 SSE 场景下每秒可能更新多次，会造成单行高频更新与死元组堆积。约定：进度写 Redis，只在 0/50/100 与状态跃迁时落库。字段保留是为了"任务结束后仍可查最终进度"。

### 4.5 向量表冗余 `dept_id`

`document_block` 冗余 `dept_id`，代价是与 `document.dept_id` 需保持同步（该字段几乎不变）。
收益：向量检索可以 **先按租户过滤再排序**，而不是"跨租户召回 topN 再过滤"——后者在租户多、单租户块少时会严重掉召回率，且一旦应用层忘记 join，就是跨租户数据泄露。

### 4.6 复合外键的代价

32 个外键中，跨表引用普遍采用 `(id, dept_id)` 复合形式，因此每张被引用表都多一个 `UNIQUE(id, dept_id)`：

- 收益：越权从"靠人写对"变成"数据库拒绝"；删除策略被迫显式化。
- 代价：写入时多一次唯一索引维护；`ON DELETE SET NULL` 在 `dept_id NOT NULL` 下不可用，故全部改为 `RESTRICT`（业务本就软删，物理删除本应被禁止）；MyBatis 不推导复合外键，需手写 SQL 映射。

## 5. 索引设计

### 5.1 按查询场景设计

| 场景 | 索引 | 说明 |
|---|---|---|
| 文件池列表（部门+分类+时间倒序） | `idx_doc_dept_cat_time (dept_id, file_category, created_at DESC)` | 字段顺序对应 WHERE→ORDER BY，避免 Sort 节点；带 `WHERE deleted_at IS NULL` |
| 解析队列 | `idx_doc_parse_pending (parse_status)` 部分索引 | 只含 UPLOADED/FAILED，体积极小 |
| 上传查重 | `idx_doc_sha (dept_id, sha256)` | 非唯一，仅用于提示 |
| 按标签筛选文件（核心） | `idx_dtr_tag_doc (tag_id, document_id)` | 关系表反向索引，v2 缺失 |
| 取某文件全部块 | `uq_block_doc_idx (document_id, block_index)` | 唯一索引兼作查询索引 |
| 复核页按租户取块 | `idx_block_dept_doc (dept_id, document_id, block_index)` | 覆盖排序 |
| 向量检索 | `idx_block_embedding` HNSW(m=16, ef_construction=64) | 余弦距离 |
| 中文子串检索 | `idx_block_content_trgm` GIN gin_trgm_ops | 让 `LIKE '%关键词%'` 走索引，替代全表扫描 |
| 任务看板 | `idx_task_dept_status (dept_id, status, created_at DESC)` | |
| 自动分配（按处理员算积压） | `idx_task_dept_assignee (dept_id, assignee_id, status)` | 覆盖 GROUP BY |
| 待派发轮询 | `idx_task_pending (dept_id, priority, created_at)` 部分索引 | 只含 PENDING |
| 租约超时回收 | `idx_task_lease (lease_expires_at)` 部分索引 | 只含 PROCESSING |
| 结果加载 | `idx_res_task (task_id, field_key)` | |
| 低置信度待复核 | `idx_res_low_conf (dept_id, confidence) WHERE NOT is_verified` | |
| 审计时间线 | `idx_task_log_task (task_id, created_at DESC)` | v2 该表**零索引** |

### 5.2 索引纪律

1. 每个索引必须对应一条具体查询，不建"以防万一"的索引（写放大与 vacuum 成本是实打实的）。
2. 单列低选择性索引（如 `field_key`）不建——v2 的 `idx_result_field` 每次写入都付出代价，却几乎不会被选中。
3. 唯一索引的前缀已覆盖的普通索引要删（如 `(task_id)` 被 `(task_id, document_id, field_key)` 覆盖）。
4. 上线后用 `pg_stat_user_indexes.idx_scan = 0` 定期巡检无用索引。

## 9. 未纳入本期（演进路径）

| 事项 | 触发条件 | 方案 |
|---|---|---|
| 分区 | `document_block` > 3000 万行，或表+索引 > 内存 1/4 | 按 `created_at` 月分区（查询需带时间范围）或按 `dept_id` hash 分区（配 local HNSW）。注意：分区后**无法建跨分区唯一约束**，`uq_block_doc_idx` 需降级为分区内唯一 |

## 10. 对 partner 设计的保留与改动

### 10.1 原样保留（不改动）

partner 的设计骨架是成立的，以下部分在 v3 中**保持原表名、原列名、原建模方式**：

| 保留项 | 原设计 | 保留理由 |
|---|---|---|
| 表名与列名体系 | `sys_dept` / `sys_user` / `document` / `task` / `extract_schema` / `extract_result` / `task_log` 等 | 已有 Java 实体与 Mapper 直接可用，改名只带来零收益的迁移成本 |
| **资产与任务解耦** | `document` 独立存在，`task` 通过 `schema_id` / `template_doc_id` / `task_document_rel` 引用文件 | 这是整套业务的建模基石（"上传 ≠ 建任务"），v3 完全沿用 |
| 三类文件同表 | `document.file_category` 区分 SOURCE / TEMPLATE / OUTPUT | 简化了"模板也是文件"的表达，避免为模板单开表再冗余一份元数据 |
| 证据溯源 | `extract_result.evidence_block_id → document_block` | 设计正确，v3 只加了 FK、`SET NULL` 策略与 `evidence_text` 快照做补强 |
| 向量内聚 | `embedding` 直接放 `document_block`，不拆独立向量表 | 当前规模下省一次 join 与一套同步逻辑；拆表留到千万级再议 |
| 标签多对多 | `sys_tag` + `document_tag_rel` 复合主键 | 标准做法，v3 只补反查索引与租户外键 |
| 动态 Schema | `schema_json JSONB` 存 LLM 生成的字段定义 | 比固定列表结构灵活得多，是"自然语言生成模板"的正确承载方式 |
| 部门邮箱配置 | `dept_email_config` 单表 + 部门内唯一 | 概念正确，v3 补的是增量位点、启停开关与授权码密文 |
| 存储分工 | 非结构化进 MinIO、结构化与向量进 PG | 分工合理，没有 objection |
| 四态 → 扩展思路 | `PENDING/PROCESSING/COMPLETED/FAILED` | 状态机方向对，v3 只是补了 `ASSIGNED`（已派未开工）与 `CANCELLED` |

**判断标准**：凡是"表集合、建模关系、职责划分"层面的设计都保留；凡是"约束、并发、隔离、审计"层面缺失的都补齐。前者是 domain 设计，后者是工程健壮性——partner 做对了前者，v3 补的是后者。

| 时间类型 | `TIMESTAMP` | `TIMESTAMPTZ` | `TIMESTAMPTZ` |
| 文件去重 | `UNIQUE(dept_id,sha256)` | 同左 | 非唯一索引 + 查重提示 |
